## Small implementation slices

1. **Isolated lifecycle fixture, not a product capability.** A manually loaded Rust test DLL creates one blank unsaved parametric hybrid design, retains exact created/prior SDK references, records immutable receipts and closes only its own fixture under strict guards. This replaces Python bootstrap for parameter qualification without claiming `new_design` parity. No startup autoload or network endpoint.
2. **Native blank `new_design`.** Validate request and bounds, reserve journal/result/identity capacity, then create once outside Command events under a checked neutral-command guard. Adopt the exact returned reference, verify parent/product/type/intent/unsaved state, and retain requested-name metadata without renaming. Unsupported `box` must refuse before admission; transaction capability remains unqualified until ported. Expose the narrower versioned native contract.
3. **Owned discard and exact-ID activation.** Separate explicit journaled operations; no active/name fallback and no bulk close. A live non-transferable ownership receipt is required for discard. Activation accepts exact current identity and a checked expected active identity. Restoring the previous active document is an explicit bounded step whose failure cannot obscure successful close.
4. **Legacy completion.** Port transaction probe and bounded recovery witness, box construction and complete inspection; then independently qualify general save/close semantics. Do not block useful blank/native parameter tests on this larger parity step.

## Ownership and identity changes

`identity::Registry::with_document` currently verifies that a leased member remains valid after its closure. It is suitable for parameter work and activation, but successful close deliberately invalidates its target. Do not bypass this check or close through that API and treat the resulting registry fault as success. Add dedicated owner-thread creation/adoption and retirement transitions with the same exclusive reentrancy guard.

Proposed internal types, not committed API:

- `CreationReservation`: non-Clone, bound to registry allocation and epoch; reserves one serial/member slot, one owned-scratch entry, and bounded receipt storage before any SDK effect. If the 256-document registry or smaller scratch limit is full, fail before `add`. Abandoning a pre-effect reservation can release capacity; post-effect uncertainty cannot evict it.
- `CreationAttempt`: reports whether invocation began, call acknowledgement, and an optional retained exact SDK lease separately from inspection errors. Preallocate the C++ lease holder before `add`. If a valid handle is returned, store it before fallible JSON/string/readback work; never let a plain `Result<Handle>` discard the only ownership proof on later failure.
- `OwnedScratch`: private live authority bound to registry epoch, journal session/create operation/request digest, exact adopted ID and retained SDK reference, original native name, initial saved/data-file observations, and supported cleanup-profile witness. Serialized receipts expose evidence, never a reconstructible native handle or authority.
- `CloseAttempt`: consumes one effect permission, invokes exact-object `close(false)` at most once, then verifies invalidity and absence in a bounded complete roster. Successful retirement removes that ID permanently. Ambiguity retains a quarantined ownership entry and forbids another close invocation under that attempt.

Creation's returned reference must match exactly one member of a complete stable post-create roster by SDK equality. Never adopt the current active object, a same-name object, a matching `creationId`, or the only list difference. Reserve the serial before invocation; keep returned references quarantined if membership/metadata verification fails. A partial roster is not evidence of absence. Nested callbacks, allocation failures, serial overflow, duplicates and release failures retain conservative fault behavior; no SDK handle crosses to the worker thread.

Public scratch acquisition requires both a coherent durable current-session successful creation receipt and the live ownership entry. A failed/unknown creation may retain a private recovery lease for diagnosis; it does not become a normal public scratch capability. Across restart, history remains readable but old scratch ownership expires. A fresh runtime must not re-adopt or close old documents using journal contents or attributes alone.

## Guards and outcomes

Before both preflight and actual create/close, check owner thread, SDK validity, bounded complete roster, and command state. Dispatch from a non-Command callback; accept only an empirically qualified exact neutral command ID, initially `SelectCommand`, with a successful getter. Unknown/empty IDs need separate qualification rather than being silently mapped to idle. If launch from Scripts Manager reports another command, refuse. A command-start event fence may strengthen this guard later, but event tracking cannot retroactively prove an already-running transaction absent. No automatic abort, `doEvents`, Undo, or `PTransaction` around lifecycle calls.

Owned discard requires exact live ownership, exact active object, unchanged original unnamed native name, `isSaved=false`, null `dataFile` with successful getter, and a supported expected-content witness. `creationId` is an additional consistency check only. A renamed/saved/replaced object or failed getter refuses before `close`. Never select a sibling object when a guard fails. If closing the last document creates a replacement Untitled, record that distinct unowned identity and leave it alone.

The first cleanup profile should be deliberately small: one component, no geometry/sketches/occurrences/features/derived or external resources, no other live preview lease, and bounded numeric user parameters. The product cleanup witness must combine root revision, complete supported parameter state/default units, and explicit empty-model/resource checks, recorded after each owned mutation. Refuse unknown or unsupported state. The r7 parameter digest alone does not prove that arbitrary user modeling work is absent; if coverage cannot be established, leave edited scratch discard unavailable instead of pretending the digest is complete. The isolated test fixture permits the expressly authorized parameter edits and clearly reports its narrower cleanup profile.

| Observation | Report and next action |
| --- | --- |
| Guard/deadline/capacity refusal before SDK invocation | Not executed; no document effect. |
| `add` invoked but throws/returns null, or identity cannot be retained | Unknown; retain available evidence, stop creation admission, never create again automatically. |
| Exact created reference retained but readback/adoption fails | Unknown with private quarantined lease; no normal public ownership claim and no guessed rollback. |
| Creation fully observed, terminal persistence/clock fails | Observed nondurable result; keep exact lease and evidence, reconciliation required. No replay. |
| Close returns true and exact object is invalid and absent in a complete roster | Observed closed; retire ID, retain close receipt, then attempt any separately authorized exact prior activation. |
| Close returns false/throws or contradicts readback | Unknown, including a false acknowledgement with apparent absence; retain raw acknowledgement and actual observation, no second close. |
| Activation returns true and actual active object equals requested exact reference | Observed activation success. Same-name equality is insufficient. |
| Activation is declined, throws, or readback fails | Report ambiguous/refused activation separately; do not try another object or conceal an already-observed create/close. |

Restoration must not steal focus from a document the user activated meanwhile: restore only if the currently active identity still matches the workflow's expected state and the retained prior object is still a unique current member. If that condition changed, leave the user's active document alone and report restoration skipped. Never re-open a closed previous document.

## Journal and shutdown integration

Retain the current coordinator sequence: bounded canonical request → durable admission/dispatch → read-only preflight → durable start → second owner-thread execution with guards repeated → observe result before terminal persistence. Reserve worst-case result bytes before effects. Creation has no pre-existing target; its start record must honestly contain operation kind, baseline/current active identity and reservation evidence, rather than inventing a target document. All owned data returned to the worker is bounded and `Send`.

Creation, close and activation have separate operation identities. Repeated same-ID/same-digest requests read status; conflicts refuse, and neither grants a new effect permission. The observer survives HTTP timeout. Use retained unknown handling for post-invocation ambiguity; do not persist an ordinary failed terminal that implies a known outcome. Durable terminal records remain authoritative. Old-session nonterminal records stay interrupted/unknown, and process-local ownership cannot be reconstructed from them. Retention/SQLite failure prevents new effects, without silently discarding already-observed receipts.

SDK lease release is not `Document.close`. Runtime stop must not close all owned or user documents implicitly. Complete explicit scratch cleanup while the service/SDK dispatcher is alive, or report the fixture as still open. Preserve existing shutdown order and uncertainty rules: stop admission, settle/cancel queue work safely, join owned workers without a main-thread callback dependency, unregister the custom event once, release all registry leases once on the owner thread, then close the SDK context. In-flight/reentrant callbacks must refuse unsafe stop. If event removal or reference release is unconfirmed, retain code/callback storage and report reconciliation; do not unload underneath retained SDK pointers or retry uncertain deletion. Add owned-resource counts/disposition to stop receipts without conflating “references released” with “documents discarded.”
